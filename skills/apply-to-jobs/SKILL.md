# Apply to jobs

Use the user's selected cv-job project and workspace. The maintained source of this adapted skill is `skills/apply-to-jobs/` in that repository; project-local and global installations are installed copies of it, not separate sources to edit. Use this cv-job variant, not the original upstream workflow. Run commands from the selected project root, never from an installed skill directory. The project supplies the CLI, candidate facts, and application records. Preserve existing customized installations before updating; do not merge conflicting same-named copies.

## Workspace and authorization

Read the selected configuration (`private/cv-job.yaml` by default), its configured instructions, candidate, experience, preferences, and ATS answers. Pass `--config PATH` before every CLI subcommand when using another workspace. Resolve YAML paths relative to the configured workspace. Do not substitute `private/profile.md`, an unrelated resume, or sample data for these sources. A contradiction between the ledger and master CV needs clarification before using that claim.

Respect the user's search scope and the workspace's role, location, eligibility, and document preferences. Candidate-specific filters belong in that workspace. Keep the master CV unchanged and do not upload it automatically. Prefer the OS credential store for newly saved passwords; preserve existing private ATS credential files using the accounts guide. Never put credentials in tracked/public files, YAML, or application records. One-time codes are transient; do not persist them.

The saved `submission` setting defaults to `review_before_submit`. An application request authorizes the work within its scope; apply any explicit authorization already given together with the saved submission and site-specific settings. Do not infer `auto_submit` from a target application count. A stricter site-specific setting, such as `greenhouse.final_submission: ask_then_submit`, requires explicit confirmation before the first submission action for that application. Once that confirmation is given, complete the associated verification/resubmit flow without asking for the same authorization again.

## Start or resume a run

1. Confirm the configuration and candidate sources exist. Run `uv run cv-job validate --check-ledger` and `uv run cv-job audit-workspace`. Investigate findings that affect the current application; retain historical records and artifacts. An unrelated historical attachment finding does not authorize rewriting the log or require abandoning other jobs.
2. Confirm the relevant browser session is signed in, or follow [accounts and verification](references/accounts.md) when registration or login is necessary. Use the connected Gmail tools only for email needed by the authorized application workflow or a requested update check.
3. Inspect `uv run cv-job applications list` and resume useful unfinished applications. Do not discard a prepared form just to start a new batch. Start a run with `uv run cv-job applications run start --target N --objective "<user request>"`; omit `--target` when the user did not set a count.

## Per-job workflow

1. **Find and record.** Read the employer, requisition, title, location, requirements, and eligibility language. Sort newest first unless the user specifies otherwise. Use [Handshake guidance](references/handshake.md) for that site; otherwise follow the named site or exact posting. Every evaluated posting gets an application-log record, including skipped or blocked jobs. Save posting text in the selected private workspace.
2. **Dedupe by opening.** Run `uv run cv-job applications check --url <url> --company "<company>" --title "<title>"`. Skip confirmed submitted duplicates and resume unfinished records when useful. Matching employer/title alone does not prove two URLs are the same opening: compare requisition and location. After confirming a board URL and ATS URL refer to one opening, link them with `applications update --id <id> --add-url <url>` instead of making another record.
3. **Check fit and evidence.** Use the workspace's hard filters rather than inventing restrictions such as remote-only or a universal role family. Skip a demonstrated hard conflict. A required answer or mandatory duration/production-depth claim without sufficient evidence is `needs_input`, not a guessed Yes or No. Nice-to-have tools alone are not a rejection. `unverified` is unknown and cannot be claimed; `listed` and `candidate_confirmed` are skills-line only, not evidence for bullets, production depth, or years. A number in `years` does not upgrade the evidence state. Gather unresolved facts once and continue jobs that do not require them.
4. **Open or reuse the record.** Use `applications add` with employer, title, URL, site, location, and `--posting-file`; inspect its help for required flags. Use the returned application folder and preserve existing documents. Record `role_orientation` when the selected workspace uses it.
5. **Prepare documents.** Follow [document guidance](references/cover-letter.md). Reuse the closest configured base, tailoring supported claims for the posting. Keep official titles, dates, tools, numbers, durations, and design/test/production distinctions intact. Save and validate job-specific resume sources and PDFs in that application's folder. A cover letter is optional unless required or useful; an optional upload field alone does not require one.
6. **Open the ATS.** Confirm HTTPS and the same employer, requisition, and location before linking an external URL. Follow [accounts and verification](references/accounts.md) for signup, login, email links/codes, or application verification. Scope account creation to the application; avoid unrelated profile changes, recruiter messages, marketing subscriptions, or other tabs.
7. **Fill from sources.** Use candidate data and explicit ATS answers. Check `applications history --company "<company>"` for prior-application questions, considering timeframe and subsidiaries. Missing history means unknown, not automatically No. Required unresolved facts become `needs_input`; leave optional unknown fields blank where allowed. Do not guess sensitive answers or consents.
8. **Review after upload.** Inspect the populated form and selected attachments after upload or replacement. Compare contact details, employers, exact titles, dates, education, authorization, notice period, compensation units, and screening answers with sources. Correct parsing errors. Confirm this job's resume is selected rather than a previously saved attachment; use its preview when available. Recheck fields affected by a replacement upload.
9. **Keep one durable record.** Save JSON details with `base`, `role_orientation`, `answers` (exact questions mapped to answers), `unresolved` (a list), and `form_check` (checked fields and mismatches). Import it with `applications update --id <id> --details-file <path> --resume <path>` and `--cover-letter <path>` only when used. Use workspace-relative attachment paths or absolute paths for the CLI to normalize. Do not introduce separate `fit.yaml`, hashes, or `answers.md`; preserve existing historical files. Never record verification tokens or credentials.
10. **Review or submit.** Required unresolved facts become `needs_input`; site/authentication failures become `blocked`, with a reason. Under `review_before_submit`, mark `review_ready`, report the form and documents, retain the resumable tab, and stop before final submit. For a site-specific `ask_then_submit`, obtain the required confirmation before the initial submit action. Under `auto_submit` or already-given applicable authorization, submit once after required fields and sensitive choices are resolved. Complete any associated email verification and resubmit step, then wait for a visible success state before recording `applied --confirmation "<evidence>"`. A click or email-code request alone is not confirmation. If the result is ambiguous, inspect the portal before retrying; do not blindly create a second submission.
11. **Finish the batch.** Close job tabs after confirmed submission or when no resumable form needs preserving. Continue other jobs when one is blocked or needs input. Do not retry a failed submission more than once. End the run with `applications run end` and `applications report`; distinguish applied, review-ready, blocked, and unresolved jobs, and include the relevant private folder paths.

## Application email updates

When asked to check status, start from tracked applications and use bounded date ranges with employer/sender or subject filters. Distinguish decisions and interview requests from receipts, alerts, and marketing. Include spam when checking for missed updates. Follow the search batching and rate-limit guidance in [accounts and verification](references/accounts.md); report the unchecked scope if access is limited. Reading email does not authorize sending, drafting, labeling, archiving, or deleting it.
